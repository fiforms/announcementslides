# Installing without Docker

> **Docker is the recommended install.** A prebuilt image (nginx, php-fpm, queue worker, scheduler and ffmpeg included) is published to `ghcr.io/fiforms/announcementslides`. If you use it, you don't need this file for installing — follow [docker/README.md](docker/README.md). (The [Google OAuth](#google-oauth-setup) and [Artisan command](#artisan-commands) sections below still apply; in Docker, set the variables in `compose.yaml` and prefix commands with `docker compose exec app`.)

This file covers running from a source checkout: a [local development install](#local-development-install), then the extra steps a [production deployment](#production-deployment) needs — the public storage symlink, the queue worker, and `ffmpeg` (the latter two both required for slide thumbnails to actually generate, the first for any uploaded media to be served at all).

## Local development install

Requirements:

- PHP 8.4+ and Composer
- Node.js / npm
- SQLite (default) or MySQL
- `ffmpeg` (for video slide thumbnails) — see [Production deployment](#production-deployment)

```bash
git clone --recurse-submodules <repo-url> announcementslides
cd announcementslides

composer install
npm install
```

(`--recurse-submodules` fetches `resources/widgets`, the bundled overlay widgets. If you
already cloned without it, run `git submodule update --init resources/widgets`.)

Copy the environment file and generate an application key:

```bash
cp .env.example .env
php artisan key:generate
```

Run database migrations:

```bash
php artisan migrate
```

Link the public storage directory:

```bash
php artisan storage:link
```

Uploaded slides, thumbnails and overlays are written to the `public` disk
(`storage/app/public`) and served from `/storage/...`. Without this symlink
the app runs, but no slide image or video renders anywhere — and nothing
reports an error, so it looks like an empty or broken install.

Point `APP_URL` at the port you actually serve on:

```dotenv
# .env
APP_URL=http://localhost:8000
```

`.env.example` ships `http://localhost`, but `composer dev` serves on port
8000. Media URLs are built from `APP_URL` (see `config/filesystems.php`'s
`public` disk), so leaving the port off produces `http://localhost/storage/...`
— port 80, where nothing is listening. The page loads fine and every image
is broken, which reads like a failed upload rather than a URL problem. Run
`php artisan config:clear` after changing it.

Build frontend assets:

```bash
npm run build
```

`composer setup` runs all of the above in one go for a first install.

### Run it

```bash
composer dev      # serve + queue worker + logs + Vite, together
composer test     # PHPUnit
```

Or start the pieces yourself: `php artisan serve`, `php artisan queue:listen` and
`npm run dev`. The queue worker matters even in development — thumbnails are generated by
queued jobs.

### Create the first user

On a fresh install, just open the site: with no users yet it redirects to a
setup wizard (`/setup`) that creates the first admin and can install the bundled
widgets. The wizard disappears once any user exists. Or from the command line:

```bash
php artisan user:create
php artisan user:setrole
```

Both commands prompt for anything you don't pass. `user:create` asks for name,
email, password and role; `user:setrole` asks for the email address and the new
role (`viewer`, `contributor`, `admin` or `banned`).

To skip the prompts, pass the values instead:

```bash
php artisan user:create --name="Jane Doe" --email=jane@example.org --password=secret123 --role=admin
php artisan user:setrole jane@example.org admin
```

Don't paste a trailing `# comment` onto these lines — zsh doesn't treat `#` as a
comment in an interactive shell, so the words become extra arguments and the
command fails with "Too many arguments".

### Load church data

```bash
php artisan church:load        # load entities for a conference from adventistdirectory.org
php artisan entity:sync        # sync the local entities table
php artisan entity:geocode     # fill in missing coordinates (U.S. addresses, for nearby sharing)
```

Admins can also do this from **Admin → Directory Import** (upload, preview, confirm).

## Google OAuth setup

To enable Google single sign-on, create OAuth 2.0 credentials in the [Google Cloud Console](https://console.cloud.google.com/):

1. Create a project and enable the **Google+ API** (or **Google Identity**).
2. Under **Credentials**, create an **OAuth 2.0 Client ID** of type *Web application*.
3. Add your app URL as an authorized origin and set the redirect URI to:
   ```
   https://your-domain.com/auth/google/callback
   ```
4. Copy the client ID and secret into `.env` (or, with Docker, the settings block of `compose.yaml`):
   ```ini
   GOOGLE_CLIENT_ID=your-client-id
   GOOGLE_CLIENT_SECRET=your-client-secret
   GOOGLE_REDIRECT_URI="${APP_URL}/auth/google/callback"
   ```

Users can then sign in with their Google account from the login page.

## Production deployment

The rest of this file covers what goes beyond the local setup above.

### Production requirements

- **`ffmpeg`** (with `ffprobe`) — used by [GenerateThumbnail](app/Jobs/GenerateThumbnail.php)
  to extract a thumbnail frame from video slides. Image slides don't need it
  (GD handles those), but any video slide will silently have no thumbnail
  without it.
  ```bash
  sudo apt install ffmpeg
  which ffmpeg ffprobe   # confirm both are on the PATH
  ```
  If `ffmpeg` isn't on the PATH the queue worker's process actually runs
  with (a common gap between an interactive shell's PATH and a
  systemd/supervisor service's PATH — check with
  `sudo -u <worker-user> which ffmpeg`), set an absolute path instead:
  ```ini
  # .env
  FFMPEG_BINARY=/usr/bin/ffmpeg
  ```
  (`config/slides.php`'s `ffmpeg_binary` key.)

### Public storage symlink (required)

`php artisan storage:link` creates `public/storage` -> `storage/app/public`.
Every slide image, video, thumbnail and overlay is written to the `public`
disk and served through that path, so without the symlink the site loads but
renders no media at all — with no error anywhere, which makes it a
frustrating first thing to debug.

```bash
php artisan storage:link
ls -l public/storage      # should be a symlink, not a directory
```

`APP_URL` has to match the URL the site is actually served on, scheme and
port included — `config/filesystems.php` builds the `public` disk's URLs from
it, so every slide image, video and thumbnail is addressed relative to
whatever it says. Get it wrong and the pages render while every piece of
media 404s, which looks like a broken upload pipeline rather than a config
value. Behind a TLS-terminating proxy that means `https://`, not `http://`.

Two deployment notes:

- **It is not idempotent across releases.** A deploy that builds into a fresh
  release directory (Envoyer, Deployer, a `releases/<timestamp>` layout) needs
  this re-run on every deploy, since the new release has no `public/storage`.
  It is already in `composer setup`, but that is a first-install script, not a
  deploy script.
- **`storage/app/public` must be the shared one.** If `storage/` is symlinked
  to a shared directory across releases (the usual arrangement), make sure the
  symlink is created after that, or a release will link to its own empty
  directory and previously uploaded slides will appear to vanish.

Related: whatever serves `public/` must never execute anything under
`public/storage`. Uploads land there, and the extension is derived from the
validated mime type rather than the client's filename (`config/slides.php`'s
`mime_extensions`), but the web server has to enforce this too.

**Beware nginx location precedence.** The usual Laravel config has a
`location ~ \.php$` block. A plain `location /storage/` prefix does *not*
shield the uploads directory from it: after matching the prefix nginx still
checks regex locations, so `/storage/x.php` would be passed to PHP-FPM and
executed. Use `^~`, which stops the regex search for that subtree. The Docker
image's `docker/nginx.conf` does this and is verified by hand against a
`.php` file in `storage/`. On your own nginx:

```nginx
location ^~ /storage/ {
    add_header X-Content-Type-Options "nosniff" always;

    location ~* \.(php[0-9]?|phtml|pht|phar|inc)$ { return 403; }

    # Uploaded SVGs are sanitized on upload (see "SVG security model" in
    # ARCHITECTURE.md); this CSP means one opened directly can never run script.
    # It does not affect SVGs shown through <img>.
    location ~* \.svg$ {
        add_header X-Content-Type-Options "nosniff" always;
        add_header Content-Security-Policy "sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:" always;
        try_files $uri =404;
    }

    try_files $uri =404;
}

# Only index.php is a PHP entry point.
location = /index.php { include fastcgi_params; fastcgi_pass ...; }
location ~ \.php$ { return 404; }
```

On Apache, use `php_admin_flag engine off` (or `RemoveHandler .php .phtml`) in
a `<Directory .../storage/app/public>` block, plus a `<FilesMatch "\.svg$">`
block with `Header always set` for the same two headers.

### Queue worker (required)

`QUEUE_CONNECTION=database` by default, which means thumbnail generation
(and anything else queued) does **nothing** until something is actually
consuming the `jobs` table. A one-off `php artisan queue:work` run from a
terminal dies the moment that session ends — production needs a persistent,
auto-restarting worker.

Check whether one is already running:
```bash
ps aux | grep "queue:work"
```
And whether anything is backed up waiting for it:
```bash
php artisan tinker --execute="echo DB::table('jobs')->count() . ' pending, ' . DB::table('failed_jobs')->count() . ' failed' . PHP_EOL;"
```

#### systemd unit

```ini
# /etc/systemd/system/announcementslides-queue.service
[Unit]
Description=AnnouncementSlides queue worker
After=network.target mysql.service

[Service]
User=www-data
WorkingDirectory=/var/web/your-domain
ExecStart=/usr/bin/php artisan queue:work --sleep=3 --tries=3 --max-time=3600
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Adjust `User=` to whichever user owns `storage/` and runs php-fpm for this
site, and `WorkingDirectory=` to the app's actual deploy path.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now announcementslides-queue
sudo systemctl status announcementslides-queue
```

`--max-time=3600` makes the worker exit cleanly every hour; `Restart=always`
relaunches it immediately. That's what actually picks up new code after a
deploy — a worker process keeps the *old* job classes loaded in memory for
as long as it runs, so without this it'd keep running stale code
indefinitely.

**After every deploy that touches a queued job's code** (anything in
`app/Jobs/`), restart the worker explicitly rather than waiting for the
hourly cycle:
```bash
sudo systemctl restart announcementslides-queue
```
Skipping this is exactly what caused a backlog of jobs to fail on
2026-08-17 — they'd been serialized against an old `GenerateThumbnail`
constructor signature and failed instantly once the worker (finally
started) tried to run them against the newly-deployed job class. That
particular symptom is a one-time migration hazard, not a recurring
one — restarting promptly after each deploy avoids the more general
version-skew case going forward.

#### Diagnosing a stuck thumbnail

```bash
php artisan queue:failed                 # see why a job failed
tail -100 storage/logs/laravel.log | grep -A5 "Video thumbnail generation failed"
php artisan queue:flush                  # clear out stale/failed jobs once resolved
```

### Backups (non-Docker installs)

Backups (`php artisan backup:create`, **Admin → Backups**, `backup:restore`) are
described in [docker/README.md](docker/README.md#backups); the same commands work
here with these differences:

- **MySQL only.** On SQLite (the local-development default) the commands and the
  admin page say so; back that up by copying `database/database.sqlite` and `storage/`.
- **Install the MySQL client tools** (`mysql-client` or `mariadb-client`) so
  `mysqldump` and `mysql` are on the `PATH` of the user running PHP-FPM, the queue
  worker and cron.
- **The Admin → Backups button needs the queue worker** (see above).
- **Scheduled backups need cron.** Nothing runs the scheduler for you here; add
  (as the app's user) `* * * * * cd /path/to/app && php artisan schedule:run >> /dev/null 2>&1`.
  Settings are the `BACKUP_*` variables in `.env` (see [config/backup.php](config/backup.php)).
- **No automatic backup before an update.** Run `php artisan backup:create` before
  `php artisan migrate` when you deploy.

### Offloading large files to Cloudflare R2 (optional)

By default every uploaded file is stored and served by this server. On a host
with metered outbound traffic (e.g. AWS Lightsail), videos, large images and
Slide Announcer updates downloaded by many devices add up quickly. With offloading
on, those files move to a [Cloudflare R2](https://developers.cloudflare.com/r2/)
bucket after upload and are downloaded from there. R2 has no egress fees.
SVGs, thumbnails, video poster frames and anything under the size threshold
stay on this server. Without these settings nothing changes.

How it works: an upload is processed here as usual (sanitizing, validation,
thumbnail, and for a video a full-size poster frame). The queue worker then
copies the file to R2, verifies it, points the database row at R2 and deletes
the local copy. Release files (app bundles, OS bundles, disk images) move the
same way. When the server itself needs an offloaded file (ZIP or REVELation
export, overlay compositing), it pulls a copy into a size-limited local cache
(`storage/app/media-cache`). "Download" buttons for offloaded files redirect to
a short-lived signed R2 link, so those bytes don't pass through this server either.

1. **Create a bucket** in the Cloudflare dashboard (R2 → Create bucket).
2. **Connect a custom domain** to it (bucket → Settings → Custom Domains), e.g.
   `media.example.org`. The domain's DNS must be on Cloudflare. Don't use the
   `r2.dev` address in production: it is rate-limited. Files are served publicly
   by their random (UUID) names, as they are from `/storage` today.
3. **Add a CORS policy** (bucket → Settings → CORS) so the web app can read images
   (Upscale/Downscale on existing images, QR checking):
   ```json
   [{ "AllowedOrigins": ["https://slides.example.org"], "AllowedMethods": ["GET", "HEAD"], "AllowedHeaders": ["*"], "MaxAgeSeconds": 86400 }]
   ```
   Use your `APP_URL` as the origin.
4. **Create an API token** (R2 → Manage API tokens) with *Object Read & Write* on
   that bucket.
5. **Set the variables** in `.env` (or the settings block of `docker/compose.yaml`):
   ```dotenv
   MEDIA_OFFLOAD_DISK=r2
   R2_ACCOUNT_ID=…            # from the R2 overview page
   R2_ACCESS_KEY_ID=…
   R2_SECRET_ACCESS_KEY=…
   R2_BUCKET=announcementslides-media
   R2_PUBLIC_URL=https://media.example.org
   # Optional, defaults shown:
   # MEDIA_OFFLOAD_MIN_BYTES=1048576     # smaller files stay here
   # MEDIA_OFFLOAD_RELEASES=true         # also Slide Announcer update files
   # MEDIA_RELEASES_WAIT_FOR_OFFLOAD=true  # hold releases back from devices until they're on R2
   # MEDIA_CACHE_MAX_BYTES=2147483648    # target size of the local cache
   # MEDIA_CACHE_MIN_AGE=60              # minutes a cached file is never evicted after use
   ```
   Then `php artisan config:cache` (non-Docker) or restart the container.
6. **Move existing files**: `php artisan slide:resync-thumbnails --posters --now`
   (poster frames for older videos, made while they're still local), then
   `php artisan media:offload --dry-run` to see what would move, then
   `php artisan media:offload` (queued; the queue worker does the work). Each
   moved file gets a new URL, so paired devices download it once more.

**Releases wait for R2.** A newly published Slide Announcer release is not offered
to devices (`app_update_available` / `os_update_available` stay false) and its
disk-image download link reads "preparing download…" until its file has finished
copying to R2. Admin → Slide Announcer Releases shows an "Uploading to storage" badge
meanwhile. Without this, a fleet checking in right after the release is tagged would
download it from this server. If the copy keeps failing, the release stays held back
(see `storage/logs/laravel.log`); retry with `php artisan media:offload --only=releases`.
This also applies to releases that already exist when offloading is switched on:
they are held back until step 6 moves them. Set `MEDIA_RELEASES_WAIT_FOR_OFFLOAD=false`
to offer releases from this server while they upload.

The queue worker and the scheduler (`schedule:run`, which trims the cache) must
be running. **Restart the queue worker after changing any of these settings**
(`systemctl restart …` or `php artisan queue:restart`): it keeps the configuration
it started with, and with offloading off in its copy the offload jobs finish
instantly without moving anything. Backups don't include offloaded files; see
[Backing up and restoring with R2](#backing-up-and-restoring-with-r2) below.

**Switching back** to a single host: remove `MEDIA_OFFLOAD_DISK`, keep the `R2_*`
settings, and run `php artisan media:localize`. This copies everything back,
points the rows here, and deletes the R2 copies (`--keep-remote` keeps them).
Until then, files already in R2 keep being served from there.

#### Backing up and restoring with R2

With offloading on, a backup comes from two places:

- **The app's backups** (`backup:create`, Admin → Backups): the database plus, for a full
  backup, the files still on this server (thumbnails, posters, SVG overlays, small images,
  widgets). They are small now that large files live in R2. Every backup's `manifest.json`
  lists the R2 objects its database refers to (`offloaded_objects`: `disk`, `key`, `size`).
- **The bucket**: large media and Slide Announcer releases. Downloading from R2 is free, so
  copy it to a desktop or NAS with [rclone](https://rclone.org/) rather than through this
  server.

**Protecting the bucket.** Deleted offloaded files are not deleted right away. They are
moved under `trash/` in the bucket (`MEDIA_TRASH_PREFIX`), so restoring an older backup
still finds them. In the bucket's settings, add an **object lifecycle rule** that deletes
objects with prefix `trash/` after longer than you keep backups (e.g. 60 days). R2 has no
object versioning. A **bucket lock** rule (e.g. prefix `slides/`, a few days) also
guards against a mass deletion. While a file is locked it can't be moved to the trash
either: deleting it leaves the original in the bucket (a warning in `laravel.log`), unused.

**Desktop mirror.** Create an R2 API token with *Object Read only* for the bucket, set up
an rclone remote for it (`rclone config`, provider *Cloudflare R2*), and run on a schedule:

```bash
rclone copy r2:announcementslides-media /backups/r2-mirror --exclude "trash/**"
```

Use `copy`, not `sync`: files deleted on the server stay in the mirror, so older backups
can still be restored from it. Each run only downloads new objects, because offloaded
objects are never rewritten. Keep the app's backup ZIPs next to it: download them from
Admin → Backups, or copy them from `storage/app/private/backups/` with `scp`/`rsync`.

To check that the mirror holds everything a backup needs (on the desktop; needs `unzip`
and `jq`):

```bash
unzip -p backup-….zip manifest.json | jq -r '.offloaded_objects[].key' |
  while read -r key; do [ -f "/backups/r2-mirror/$key" ] || echo "missing: $key"; done
```

On the server, `php artisan media:verify` checks every file the database refers to:
local files, and offloaded files in the bucket. Offloaded files found in the bucket trash
can be moved back with `--restore-trash`. `--mirror=<folder>` also checks a mirror on
the server, by name and size. It exits non-zero if anything is missing.

**Restoring.** Start every restore the same way: a working install, then
`php artisan backup:restore <backup.zip>` (see [docker/README.md](docker/README.md#restoring)),
then restart the queue worker. Then pick the case that applies:

1. **The server was lost, the bucket is intact** (the usual case). Use the same `R2_*` and
   `MEDIA_*` settings (and ideally the same `APP_KEY`) on the new server. After the
   restore, run `php artisan media:verify --restore-trash`. That brings back any file
   deleted after the backup was taken, as long as it is still in the trash. Nothing else
   to do: URLs are unchanged, so devices notice nothing.
2. **The bucket lost objects** (deleted bucket, deleted files, account problem). Point the
   `R2_*` settings at the bucket (or a new one, with its custom domain in `R2_PUBLIC_URL`),
   upload the mirror, then verify:
   ```bash
   rclone copy /backups/r2-mirror r2:announcementslides-media \
     --header-upload "Cache-Control: public, max-age=31536000, immutable"
   php artisan media:verify
   ```
   Uploading to R2 is free. The mirror may hold more than the backup needs; extra
   objects are harmless.
3. **Restoring onto a single host without R2.** Leave `MEDIA_OFFLOAD_DISK` unset. Copy the
   mirror into the local disk (its folders match the storage paths), point the rows at
   it, then verify:
   ```bash
   rsync -a --exclude 'trash/' /backups/r2-mirror/ storage/app/public/
   chown -R www-data:www-data storage/app/public
   php artisan media:localize --relink     # only rows whose file is now here (right size)
   php artisan media:verify
   ```
   `--relink` downloads and deletes nothing. Rows whose file is missing locally keep
   pointing at R2 and are listed by `media:verify`.

Missing thumbnails, posters and composites can be rebuilt with
`php artisan slide:resync-thumbnails --all --posters --now`.

**Purging archived media (optional).** To keep the bucket from growing forever, the
offloaded files of slides that expired or were deleted more than 180 days ago
(`MEDIA_PURGE_ARCHIVED_DAYS`) can be removed from the bucket, while their records,
thumbnails and posters stay. Archived slides still appear in the church's archive with a
preview and a note that the full file is in offline storage. Only files in R2 are purged;
files on this server are left alone.

- **Back the bucket up first.** Run `rclone copy` before purging: once the trash lifecycle
  rule has run, the mirror holds the only copy.
- **Try it by hand:** `php artisan media:purge-archived --dry-run -v` lists what would go.
  Then run `php artisan media:purge-archived` (`--days=N` overrides the age).
  `MEDIA_PURGE_ARCHIVED=true` runs it daily.
- **Purged files go to the bucket trash** like any deleted file. Un-archiving a slide
  brings its files back automatically while they are still in the bucket or its trash.
  After that, un-archiving says the media is missing. Upload the mirror to the bucket
  (`rclone copy /backups/r2-mirror r2:<bucket> …`, as in case 2 above), then run
  `php artisan media:purge-archived --restore`.
- **`media:verify`** skips purged files on archived slides, but flags purged media on a
  slide that is back in use.

#### Other S3-compatible providers (e.g. Backblaze B2): not yet supported

Offloading only depends on a Laravel filesystem disk: [MediaStore](app/Support/MediaStore.php),
the media cache, the offload jobs and the `media:*` commands work with any disk name
set in `MEDIA_OFFLOAD_DISK`. Only the `r2` disk is configured and tested. Backblaze B2
looks feasible, but these points would need to change or be checked first:

- **Why B2 might be chosen:** storage is cheaper (about $6.95/TB/month against R2's ~$15),
  but downloads are only free up to 3× the stored data, then $0.01/GB, unless they go
  through a partner CDN such as Cloudflare (unlimited free egress). R2 makes all
  downloads free without conditions. B2 pays off when far more data is stored than
  downloaded (e.g. as a backup target); this app mostly serves the same media many times.
- **A `b2` disk** would be added in [config/filesystems.php](config/filesystems.php) next to `r2`:
  driver `s3`, endpoint `https://s3.<region>.backblazeb2.com`, region e.g. `us-west-004`,
  `use_path_style_endpoint` true, `throw` true, and `B2_*` env variables (plus
  `.env.example` / `docker/compose.yaml`).
- **Public URL (`url`):** B2's public download URL has a path prefix:
  `https://f00X.backblazeb2.com/file/<bucket>/<key>`. Setting `url` to
  `https://<host>/file/<bucket>` gives correct `file_url`s without a rewrite rule.
  Devices need these URLs to be direct and stable (see *Storage tiers* in
  ARCHITECTURE.md), so a public bucket is required, as with R2.
- **Cloudflare in front (for free downloads):** use a proxied CNAME (e.g. `media.example.org`)
  to the `f00X.backblazeb2.com` host, with `url` set to `https://media.example.org/file/<bucket>`.
  Check two things: Cloudflare's self-serve CDN terms allow limits on sites that mainly
  serve video or other large files through the CDN (this doesn't apply to R2), and the
  free plan doesn't cache files over ~512 MB (e.g. OS disk images), so those are
  fetched from B2 every time.
- **ACL header (verify):** Laravel's S3 driver sends an `x-amz-acl` header (`private`
  by default) on every write, and B2's S3 API documents ACLs as unsupported (access is
  set per bucket). Test whether B2 ignores or rejects it. If it rejects it,
  `MediaStore::copyToOffload()` / `copyToLocal()` would need to skip the ACL for that
  disk (or the disk's `visibility` set to match the bucket).
- **Download filenames (verify):** `MediaStore::download()` redirects to a presigned URL
  with `ResponseContentDisposition` so the file downloads under the slide's title. B2
  supports SigV4 presigned URLs, but it's unconfirmed whether its S3 API honours
  `response-content-disposition`. If it doesn't, downloads would get the UUID name.
  The fallback is to stream offloaded downloads through the app for that disk, which
  costs host egress, or to use B2's native `b2ContentDisposition` authorization.
- **Cache-Control (verify):** offloaded objects are written with
  `Cache-Control: public, max-age=31536000, immutable`. Check that B2 stores this header
  and returns it, so Cloudflare caches the files.
- **CORS:** B2 sets CORS rules per bucket (`b2 bucket update --cors-rules` or the web UI).
  The same GET/HEAD rule for `APP_URL` as for R2 is needed.

  real bucket: upload, offload, device sync, "Download" button, ZIP export.
