# hotfixes/

Surgical OS-level patches for already-deployed Slide Announcer devices. Same
mechanism as the platform's own hotfixes (`slideannouncer/image-builder/
make-hotfix-bundle.sh`, which explains the safety constraints), but the
sources live here with the product, so this repo needs no change inside the
`slideannouncer/` submodule.

## Is a hotfix what you need?

A hotfix patches files on the device's **root filesystem** in place, and has
**no A/B rollback**. It is for OS-level things: systemd units, nginx config,
polkit rules, scripts in `/usr/local/sbin`, `config.txt`-style settings.

| Change | How it ships |
|---|---|
| Product code: `backend/`, `frontend/` (sync, kiosk, widgets, settings UI) | **The app updater.** Bump `slideannouncer/local-app/VERSION`, `npm run package:slideannouncer`, upload the tarball under Admin → Slide Announcer releases. App code lives on `/data/local-app`, not the rootfs, so a hotfix can't (and shouldn't) carry it. |
| OS files (units, nginx, polkit, system scripts), no new packages | **A hotfix** (this directory). |
| New apt packages, kernel, partitioning, anything a hotfix can't express | A full image: `npm run build:slideannouncer`, then OTA or reflash. |

The existing hotfixes follow this split: e.g. the 0.3.9 hotfix changed nginx
for the new SRT bridge while its backend/frontend shipped through the updater.
A product change that needs both (say, new app code plus an nginx tweak) is two
releases: the hotfix first, then the app update.

## Versions are pairs

A device's OS version is `<platform>_<product>`: the platform's
`slideannouncer/image-builder/VERSION` plus this product's `image/VERSION`
(see `slideannouncer/docs/PRODUCTS.md`). The app has its own pair, from
`local-app/VERSION` plus this product's `VERSION`, and ships through the app
updater, not here.

The on-device hook refuses to run unless `/opt/slide-announcer/VERSION` reads
exactly `<required-version>`, then sets it to `<new-version>`. So hotfixes form
**one linear chain per device**, shared with the platform's own hotfixes in
`slideannouncer/image-builder/hotfixes/`. Two kinds of step:

- **A change in this product's OS files** (the common case here): bump
  `image/VERSION` and build `0.4.1_0.1.0` -> `0.4.1_0.1.1`. The platform part
  doesn't move, and nothing in the submodule changes.
- **A change in the platform:** that's a platform hotfix, `0.4.1_0.1.0` ->
  `0.4.2_0.1.0`, built from the submodule's `image-builder/hotfixes/`.

Before choosing versions, find where the devices are: the current
`image-builder/VERSION` + `image/VERSION` is the latest *image*, and each
hotfix directory's `build.sh` shows the step it makes. A device that is not
exactly at `<required-version>` rejects the bundle and is left untouched.
Devices from before pairs existed report a plain `0.4.0`; the platform's
`0.4.1` hotfix moves them to `0.4.1_<image/VERSION>`.

## Making one

```bash
# bump kiosk-products/slideannouncer/image/VERSION to 0.1.1 first, then:
npm run hotfix:new:product 0.4.1_0.1.0 0.4.1_0.1.1 "what it fixes"
# put the files to patch under kiosk-products/slideannouncer/hotfixes/0.4.1_0.1.1/files/
#   (same layout as the device's /, e.g. files/etc/systemd/system/foo.service)
# edit 0.4.1_0.1.1/build.sh's header comment, and script.sh (or delete it)
npm run hotfix:build:product 0.4.1_0.1.1
```

One directory per hotfix, named for the version it bumps *to*:

- `build.sh` — required/new version, then calls the platform's
  `make-hotfix-bundle.sh` (generated by `new.sh`; you rarely edit past the
  header comment).
- `files/` — copied verbatim onto the device's root. Everything lands
  `root:root`. Keep it to what you are actually patching.
- `script.sh` — optional; runs once on the device after extraction and before
  the version bump, for things a file copy can't do. It is not chrooted: use
  `$ROOT` (`systemctl --root="$ROOT" enable foo.service`, `rm -f "$ROOT/etc/…"`).
  A nonzero exit aborts the hotfix before the version is bumped.

## Commands

| Command | Does |
|---|---|
| `npm run hotfix:new:product <required> <new> "what it fixes"` | scaffold a product hotfix directory |
| `npm run hotfix:build:product <new>` | build one of this product's hotfixes (directory name, e.g. `0.4.1_0.1.1`) |
| `npm run hotfix:build:core <version>` | build one of the platform's hotfixes from the submodule, for this product (directory name, e.g. `0.4.1`) |

## Building

Needs `rauc`, and `RAUC_CERT_PATH`/`RAUC_KEY_PATH` in
`slideannouncer/image-builder/.env` (the same signing pair as full builds).
The bundle is stamped with this product's RAUC `compatible`
(`slideannouncer-rpi4`) and lands in `slideannouncer/image-builder/deploy/` as
`slideannouncer-<new>.hotfix.from.<required>.raucb`, e.g.
`slideannouncer-0.4.1_0.1.1.hotfix.from.0.4.1_0.1.0.raucb`.

## Installing

Upload the `.raucb` under Admin → Slide Announcer releases, or on a dev build
(`SSH_DEV_BUILD=1`) run `rauc install <path-or-url>` on the device. Anything
touching a unit or nginx config takes effect after a reboot, since the hook
can't restart running services. Test on a spare Pi first: there is no
fallback slot if a hotfix is wrong.
