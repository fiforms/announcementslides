# Architecture

AnnouncementSlides is a web application for distributing announcement slides to
Seventh-day Adventist churches. A conference admin (or authorized contributor)
publishes slides that any church in the system can display; church leaders
manage slides scoped to their own congregation; and registered viewers can
submit slides for review. It replaces an error-prone email workflow where
admins emailed slides to pastors who forwarded them to A/V teams.

This document describes how the project is laid out and where each piece of the
implementation lives.

## Stack

- **Backend:** Laravel (`laravel/framework` ^13.8, PHP ^8.4) — see [composer.json](composer.json)
- **Frontend:** Vue 3 + [Inertia.js](https://inertiajs.com/) (no separate REST API; controllers return Inertia page responses) + Tailwind CSS, bundled with Vite — see [package.json](package.json)
- **Auth:** Laravel Breeze (email/password) plus optional Google OAuth via Laravel Socialite
- **i18n:** `vue-i18n` on the frontend ([resources/js/i18n.js](resources/js/i18n.js)); slide content is also language-*tagged* server-side (see below)
- **Database:** SQLite in dev, MySQL in prod
- **File storage:** Laravel Storage. Everything is uploaded to and processed on the local `public` disk. Optionally, large files are then offloaded to Cloudflare R2 (see *Storage tiers*). Files are never stored in the DB; only metadata rows. See [config/filesystems.php](config/filesystems.php) and [config/media.php](config/media.php).

## Request lifecycle

1. Routes are declared in [routes/web.php](routes/web.php) (app) and [routes/auth.php](routes/auth.php) (Breeze auth). Console commands register in [routes/console.php](routes/console.php).
2. App bootstrapping, middleware, and aliases live in [bootstrap/app.php](bootstrap/app.php). The Inertia middleware [HandleInertiaRequests](app/Http/Middleware/HandleInertiaRequests.php) shares the authenticated user, their entity memberships, and flash messages with every page.
3. Controllers in [app/Http/Controllers/](app/Http/Controllers/) return `Inertia::render('SomePage', [...])`, which maps to a Vue component in [resources/js/Pages/](resources/js/Pages/).
4. The root Blade shell is [resources/views/app.blade.php](resources/views/app.blade.php); the JS entrypoint is [resources/js/app.js](resources/js/app.js).

## Roles & access control

There are two independent permission layers:

**Global role** (`users.role`): `admin`, `contributor`, `viewer`, `banned`. Checked via helpers on [User](app/Models/User.php) (`isAdmin()`, `isContributor()`, `isBanned()`).
- Admin routes are gated by [EnsureAdmin](app/Http/Middleware/EnsureAdmin.php) and live under `/admin`.
- Banned users are blocked by [EnsureNotBanned](app/Http/Middleware/EnsureNotBanned.php) (aliased `not-banned` in [bootstrap/app.php](bootstrap/app.php)).

**Per-entity role** (`user_entities.role`): a user can hold a role on one or more churches independent of their global role (entity-scoped actions never check `users.role`, so a new editor needs no global promotion). Three tiers:
- `viewer` — a follower (self-service subscribe).
- `editor` — manages the entity's slides, shows, shared links, devices and archive, exactly like a leader.
- `admin` — the entity **leader**: everything an editor does, plus the Team page (`/entity/{entity}/people`, [EntityPeopleController](app/Http/Controllers/EntityPeopleController.php)) which lists every leader/editor/follower and lets them add or revoke **editors only**. Leaders are only ever changed by a site admin (Admin → Users, Directory Import, `entity:assign`), and removing/replacing a pastor never touches the editors they added.

`User::isEntityAdmin()` / `adminEntities()` / `leaderEntityIds()` mean "may manage" and include editors (`User::MANAGER_ENTITY_ROLES`); `isEntityLeader()` / `ledEntityIds()` are the strict leader-only checks used for people management. A leader inviting an email with no account creates an [EntityInvitation](app/Models/EntityInvitation.php), redeemed (`redeemFor()`) when that address signs in with Google or verifies its email, so an unverified password signup can't claim it. Resolved via `User::entityRole()` and `memberEntityIds()`.

### First-run setup wizard

While the `users` table is empty the app offers `/setup` ([SetupController](app/Http/Controllers/SetupController.php), page `Pages/Setup/Index.vue`), which creates the first `admin` (email pre-verified, signed in on success) and optionally installs the bundled widgets listed in [config/setup.php](config/setup.php) through `WidgetInstaller`. The gate is [FirstRunSetup::needed()](app/Support/FirstRunSetup.php): [EnsureSetupIsOpen](app/Http/Middleware/EnsureSetupIsOpen.php) 404s both routes as soon as any user exists, and the controller re-checks under a cache lock so two simultaneous submissions cannot create two admins. [RedirectToSetup](app/Http/Middleware/RedirectToSetup.php) sends the home, login and register pages there while the install is empty (`SETUP_REDIRECT=false` disables it; the test suite does). `SETUP_TOKEN`, when set, must be entered on the form; empty means open, which suits a local test but not an exposed one. `auth.password_login` (`PASSWORD_LOGIN`) controls whether the email/password login form is shown at all (default: only in the `local` environment); `POST /login` works regardless. The Docker compose file sets both for a test-friendly default (see [docker/README.md](docker/README.md)).

## In-app help

Help is Markdown in [resources/help/](resources/help/), one folder per language (`resources/help/<locale>/<topic>.md`), rendered by [HelpLibrary](app/Support/Help/HelpLibrary.php) (league/commonmark; raw HTML stripped, unsafe links refused). Config is [config/help.php](config/help.php); authoring rules (front matter, `help:` topic links, `media:` images/videos/captions) are in [resources/help/README.md](resources/help/README.md).

- **Localization:** the language is `?lang=` if given, else the browser's `Accept-Language` among `config('help.locales')`, else English. A topic missing in that language falls back to English per topic and is flagged `fallback` (the page shows a notice), so translations can land one file at a time. The language switcher appears once a second language has content. The server does not know the vue-i18n locale (it is detected in the browser), so help does its own negotiation. UI strings are in `help.*` / `nav.help` in the locale JSON files.
- **Audience:** a topic's `audience` front matter (`everyone` | `users` | `managers` | `admin`) hides it from the index and 404s it for others. The pages themselves are public like About.
- **Media:** `![alt](media:name.png)` resolves to the reader's language folder, then English, then shared `resources/help/media/`; `.mp4`/`.webm` render as a `<video>` (with a same-name `.vtt` as captions) and a full `https://` URL to a video does too. Files are served by `HelpController::media` (Range-capable) only for allowed extensions under a `media/` folder (no SVG). Keep large videos out of git and link them by URL.
- **Linking from pages:** `<HelpLink topic="…" />` ([HelpLink.vue](resources/js/Components/HelpLink.vue)) renders a "?" to a topic.
- **Adding a topic:** add `resources/help/en/<slug>.md`; the test `HelpTest::test_the_bundled_english_topics_are_well_formed` checks titles, missing media and broken `help:` links.

## Data model

Models live in [app/Models/](app/Models/); schema in [database/migrations/](database/migrations/).

- **[Slide](app/Models/Slide.php)** — the central model. Stores metadata (`title`, `notes`, `text_description`, `link`), scheduling (`publish_at`, `expires_at`), a workflow `status` enum (`draft`/`pending`/`published`/`rejected`), `sort_order`, soft deletes, and FKs to `uploaded_by`/`reviewed_by` users, an optional `entity_id`, and an optional `language_id`. A `share_nearby` flag rounds it out. A slide's actual files live on its `media` relationship (see `SlideMedia` below) rather than on the `Slide` row itself — and a slide may have **no image at all** (see *Slides with no image*); `Slide` exposes back-compat proxy accessors (`file_url`, `thumbnail_url`, `mime_type`, `original_filename`, `file_size`, `isImage()`/`isVideo()`) that resolve against `primaryMedia` (its `slide`-type file), so single-file-per-slide views keep working unchanged.
- **Public tokens** — slides, shows and promo shows (`GlobalShowTemplate`) each have a unique `token` (6 vowel-free random characters, or a link name like `camp26` chosen at upload by a contributor/admin, never an entity leader) generated by [PublicToken](app/Support/PublicToken.php) via the `HasPublicToken` trait (slides: [SlideToken](app/Support/SlideToken.php); a promo's link name can be chosen at upload the same way). It is the only identifier in public URLs (`/slides/{slide:token}`, `.../download`, `.../media/{media}/download`, `/?show=<token>`, `/?promo=<token>`, download `?ids=<slide tokens>`) and is immutable after creation; numeric ids still key the authenticated admin/editor routes. `?show=` only resolves a show belonging to the requested `entity_id` (or a global show when there is none). Anything entity-scoped (`/?entity_id=`, `/archive?entity_id=`, and the show/ZIP/PowerPoint/REVELation downloads with an `entity_id`) is private to that church's members and site admins (`SlideController::authorizeEntityView()`: guests go to login, others get 403); global views stay public. Slide/attachment downloads also require the slide to be visible to the viewer. A church's **archive** (`/archive?entity_id=`; there is no global archive page — and an archived local slide's own link/download — `Slide::hidingArchivedLocalFrom()`) is for that church's leaders only (`User::leaderEntityIds()`), not followers or site admins. `entities.allow_subscription` (default on; leaders toggle it on their Entity Slides page) controls whether others may subscribe: when off, `User::viewableEntityIds()` drops the entity for `viewer` followers (leaders and site admins keep access; Play Link kiosks never depended on membership), so every visibility check uses `viewableEntityIds()` rather than `memberEntityIds()`. A slide link only opens a *released* slide (`Slide::released()`: published, past `publish_at`) that is `visibleToUser`, so drafts and pending submissions never open from a link.
- **[SlideMedia](app/Models/SlideMedia.php)** — one row per file attached to a `Slide`. `media_type` is a plain string (`slide`, `slide-overlay`, `color-flyer`, `easy-print-flyer`, `social-media-image`, …) validated against `config('slides.media_types')` rather than a DB enum, so adding a new type is a config change, not a migration. A slide normally has one `slide`-type row (seeded at upload time; it can be removed, see *Slides with no image*); the rest are optional variants attached later from the Edit screens (`ManagesSlideMedia` trait, `.../{slide}/media` routes). Carries the same file/thumbnail/image-quality fields the old `Slide` row used to (`disk_path`, `mime_type`, `thumbnail_path`, `image_width`/`image_height`, `validation_issues`/`validation_status`), plus an `overlay_settings` JSON column that holds an overlay's validated **widget placements** (`{widgets: [...]}`; see *Overlay widgets* below). The rest of the editor's source stays inside the SVG. It also carries `variants`/`active_variant` for AI-upscaled images (see *AI upscaling* below): the row's own file columns always describe the *active* version, so nothing that reads a media row needs to know about upscaling.
- **Show frame** — a show can carry an optional *frame*: a background image/video under every slide and an overlay (SVG + live widgets) over every slide. The pieces are ordinary `SlideMedia` rows that belong to a show instead of a slide (`slide_id` null, `show_id` set; `media_type` `show-base` / `show-overlay`, listed in `config('slides.show_media_types')`), reached through `Show::baseMedia()` / `overlayMedia()`. Layer order, bottom to top: show background → slide image → slide overlay → slide widgets → show overlay → show widgets. See *Show frame* below.
- **[User](app/Models/User.php)** — global role, optional `google_id`/`avatar_url`, a many-to-many to `Entity` through `user_entities`, and per-user key/value settings via [UserSetting](app/Models/UserSetting.php) (`setting()` / `putSetting()`).
- **[Entity](app/Models/Entity.php)** — a church/organization that owns local slides and has members. Carries `latitude`/`longitude` for nearby sharing and a `deactivated` flag.
- **[AdventistEntity](app/Models/AdventistEntity.php)** — a *raw import* table of congregations scraped from adventistdirectory.org (richer fields: pastor, socials, conference code). This is the source data; `entity:sync` distills it into the working `Entity` table.
- **[Language](app/Models/Language.php)** — supported languages (`abbreviation`, `name`, `native_name`); seeds English + Spanish.
- **[UserInvitation](app/Models/UserInvitation.php)** — admin-issued invitations.

### Slide visibility & workflow (query-time, no cron)

[Slide](app/Models/Slide.php) defines query scopes that encode all the business rules:

- `current()` — published, publish date passed, not expired.
- `archived()` — published but expired.
- `upcoming()` — published but publish date still in the future.
- `pendingReview()` — `status = pending` (the submission queue).
- `unscoped()` / `entityScoped()` — global slides vs. one church's slides.
- `visibleToUser()` — global slides plus slides for entities the user belongs to.
- `shareNearby()` — slides a church has opted to share with neighbors.
- `language()` — current language *or* untagged (untagged slides show in every language).

Because expiry/publishing is computed at query time, no scheduled job is needed. `getDisplayStatusAttribute()` derives `scheduled`/`archived` labels for the UI.

### Slides with no image

A slide's base image/video is optional. The **Create or Upload** form (`UploadPanel`, and the admin Slides page) saves a slide from an image *or* just a title (`ChunkedUploadController::finalize` accepts no `uploads`, then needs a title; a file with no title takes its name), and the Edit screens' media manager can remove a slide's `slide` file (`destroyMediaForSlide`), leaving the slide in its shows. Such a slide may carry only an overlay and/or widgets (widget placements live on the overlay row), or nothing.

- **Visibility:** [Slide::scopeWithContent()](app/Models/Slide.php) (an image/video *or* an overlay) is applied to the play-link payload and the device `shows` sync, so a slide with nothing is an *invisible placeholder*: it stays in the show for editing but is never played. The legacy flat device sync (`index()`) uses `withBase()` since old kiosk builds need a file for every slide.
- **Players:** `SlideStage` (web and kiosk) only waits for media that exists; the device sync stores `local_filename` null for a slide with no file, and its playlist keeps a slide that has a base file, an overlay file or widgets.
- **Thumbnails:** `SyncOverlayThumbnail` flattens an image-less slide's overlay (and widget stand-ins) onto a black 600×338 canvas (`OverlayCompositor::flatten()` takes a null base).
- **Exports:** the PowerPoint draws an overlay-only slide on black, the `.revel` snapshot writes it as its overlay image plus the widget blocks, and the zip skips it (no image file).
- **Nearby sharing** needs an image: finalize ignores `share_nearby` without a file, `shareNearby` refuses, the pages disable it, and removing a shared slide's image unshares it.

### Immutable global slides

An admin can mark a global slide `immutable` (Admin → Edit slide). While it is published and unexpired ([Slide::isLockedInShows()](app/Models/Slide.php)), a leader can't remove it from their entity's **Main Show** (`ShowController::detach` returns 422; the Show Editor tags it "Required"). Extra shows are unaffected. Turning the flag on re-adds the slide to every Main Show via `Show::restoreImmutableSlide()` (run from the `SyncShowAutoFillForSlide` job). Expiry, un-publishing or clearing the flag releases the lock.

### Nearby sharing

A church viewer can opt to also pull in slides from nearby congregations. [NearbyEntities::within()](app/Support/NearbyEntities.php) does a cheap SQL bounding-box pre-filter, then refines to an exact great-circle (haversine) radius in PHP so it stays DB-portable. The radius default is [config/slides.php](config/slides.php) (`SLIDES_NEARBY_RADIUS_MILES`, default 50), overridable per user via the `nearby_radius_miles` setting. Only the *borrowed* bucket is gated by the `share_nearby` flag.

### Shared playback links

A leader can mint a revocable, titled link per screen ("Hallway TV") on `/play-links`. [PlayLink](app/Models/PlayLink.php) stores a 64-character random `token` (the URL secret, kept readable so the link can be copied again), the entity, an optional `show_id` (null follows the Main Show), an optional `language_id` (null plays all), `delay_seconds`, `last_used_at` and `revoked_at`. `/play/{token}` needs no login: [PlayController](app/Http/Controllers/PlayController.php) derives everything from the link (never the query string) and renders `Pages/Play/Show.vue`, which runs [SlideshowModal](resources/js/Components/SlideshowModal.vue) in `kiosk` mode (no controls, no fullscreen prompt). The open page polls `/play/{token}/slides` so slide edits, a changed delay and revocation reach an unattended screen; a 404 stops playback. Pages send `no-store`, `Referrer-Policy: no-referrer` and `noindex`; the routes are throttled per IP. Widgets on entity-local slides can't be read by a guest, so their `data_url`s are rewritten to the link's own `play.widget-data` endpoint (`WidgetDataController::playLink`), limited to slides in the link's show.

### Show frame

An entity admin sets a show's frame on the Show Editor (**Show frame** panel in [Shows/Manage.vue](resources/js/Pages/Shows/Manage.vue); `ShowController` `shows.media.store` / `.destroy` for the background and `shows.overlay.show` / `.save` for the overlay). The background goes up through the same chunk endpoint as any slide file and replaces the previous one; the overlay is the ordinary [OverlayEditor](resources/js/Components/OverlayEditor/) pointed at the show (`routeModel`, `background` props), saved by the same `ManagesSlideMedia` code as a slide's overlay, so its widgets are validated into `overlay_settings` by [OverlayWidgets](app/Services/Widgets/OverlayWidgets.php) exactly as for a slide. Frame media is for one entity's show only (no global or conference-wide frames yet).

[ShowFrame](app/Services/ShowFrame.php) turns a frame into what players receive (`file_url`, `mime_type`, `overlay_url`, `overlay_widgets` for browsers; the device version adds `overlay_media_id` and un-URLed widgets), or null when the show has none. Players mount it **once, outside the per-slide fade**, as two [ShowFrameLayer](resources/js/Components/ShowFrameLayer.vue) instances: `base` under the slide stages and `top` over them, so a clock never fades or reloads and a background video never restarts on a slide change. A slide stage is transparent, so the background shows through transparent PNG/WebP slides and during crossfades.

**Background music.** A show can also play audio from the library, independent of its background (so music can sit under an image, an uploaded video, YouTube or a live channel, or be the only thing in the frame). Library audio is `library_items.kind = 'audio'` (MP3, M4A, WebM audio): uploaded through the chunk endpoint as `media_type` `library-audio` (kept out of `config('slides.media_types')` so it never shows as slide media), adopted by `LibraryController::storeAudio`, which checks it with [AudioProbe](app/Services/AudioProbe.php) (ffprobe: rejects files with no audio stream, records `duration_seconds`) and stores it content-addressed under `library/audio/<aa>/<sha256>.<ext>`. There is no thumbnail, so an audio item is ready as soon as it has a file; `LibraryFiles` sweeps and `OffloadLibraryItem` treat it like a background. A show's music is the ordered `show_audio` pivot (`Show::audioItems()`) plus `shows.frame_audio_volume` and `shows.frame_audio_shuffle`; `ShowController::saveAudio` takes `library_item_ids` (the whole ordered list, distinct, up to 50; empty clears it) and the Show Editor edits it as a playlist with add / reorder / remove. Deleting a library item removes it from every show (cascade). Players get `frame.audio = {tracks: [{id, url, mime_type, title}], volume}`; [FrameAudio.vue](resources/js/Components/FrameAudio.vue) (and its kiosk twin) plays a lone track with `loop` and several in order, restarting after the last (a track that fails to load is skipped). With shuffle each pass is a fresh random order that never opens with the track that just played. It rests while the player is paused and during a video slide that has its own sound. Library background videos are silent backdrops by default: `library_items.has_sound` (false unless the admin ticks "has sound" on upload or toggles it on the item) is copied to `slide_media.muted` when a slide is built (`LibrarySlides::attachBackground`; toggling the item updates the sharing rows), exposed to players as `video_muted`, and both players mute that video and leave the music playing. Ordinary uploaded videos are unmuted and still pause the music. The Slide Announcer caches each track as `show-<id>-audio-<library item id>.<ext>` (`sync.py` `_sync_frame_audio`), so music keeps playing offline. Not covered yet: the kiosk's idle interlock (`stream_timeout_hours`) only stops YouTube/live-channel streams, not music. MP3 loops can have a tiny gap from encoder padding; M4A/WebM loop more cleanly.

**YouTube background.** Instead of an uploaded file, the background can be a YouTube video or playlist (`shows.frame_youtube`, set by `ShowController::saveYoutube`; exclusive with an uploaded `show-base`). [YoutubeSource](app/Support/YoutubeSource.php) reduces whatever is pasted to validated ids (anything not on a YouTube host is rejected; only ids are stored) and is the only place the embed URL is built — always `youtube-nocookie.com`, autoplay, looping, no controls, `enablejsapi=1`. Players get it as `youtube_url` and check its prefix again before putting it in a sandboxed iframe, sized 16:9 and centred like the other layers. It needs the internet: the kiosk mounts the iframe only while online, pauses/resumes it with `postMessage` when the show is paused or an external feed plays, and nothing is cached on the device. Browsers may keep its sound off until the page is interacted with (the kiosk's Chromium plays it with sound); the `muted` flag adds `mute=1`. It counts as a background video for the rule below.

**Background video rule:** if a show's background is a video, uploaded or YouTube (`Show::skipsVideoSlides()`), slides whose primary media is a video are left out of playback entirely — the server omits them from the play-link payload and the device sync (`Slide::withoutVideo()`), and the device's playlist builder drops stragglers — so two videos never play at once or mix audio. The background loops and plays with sound; the kiosk pauses it while the show is paused or an external feed is on screen. Only the shared-link player (`/play/{token}`, which knows its show) and devices render a frame; the general web slideshow (`/`) isn't tied to a show and doesn't.

Widget data for frame widgets reuses the three existing endpoints (`widget-data.show`, `play.widget-data`, the device route): each accepts a `show-overlay` media row, authorized by entity membership, the link's own show, or the device's entity.

### Bulk downloads

[SlideController](app/Http/Controllers/SlideController.php) can package the currently-visible slides as a **ZIP** (`downloadZip`) or assemble them into a **PowerPoint** deck (`downloadPowerPoint`) using `phpoffice/phppresentation` — each image is centered, aspect-fit onto a black 16:9 slide.

A slide whose primary file is over `slides.zip_max_media_bytes` (`ZIP_MAX_MEDIA_BYTES`, default 10 MB; 0 = no limit), typically a video, is left out of the ZIP. A `Large files not included.txt` in the archive lists each one's title, size and link instead. The size is checked before `localPath()`, so an offloaded file is never fetched just to be zipped. The slides page gets the limit (`zipMaxMediaBytes`) and each slide's `file_size`, and shows a dismissible notice naming the excluded slides when a ZIP download starts. PowerPoint exports are not affected.

A `.revel` download links large media instead of embedding it. A base file over `slides.revelation_link_media_bytes` (`REVELATION_LINK_MEDIA_BYTES`, defaults to the ZIP cutoff; 0 = always embed) becomes a front-matter `media:` alias (`filename` = our UUID file name, `title`, `mediatype`, `description`, `url_direct` = its public URL, on R2 when offloaded), and the slide references `media:<alias>`. When the file is opened, REVELation offers to download it into the user's media library and links it there. The video is never fetched by this server, and users download it once however many decks use it. The page shows a matching notice when the download starts. The link works only while the file exists (until the slide is deleted); files already in a user's library keep working.

## Uploads, validation & thumbnails

- **Chunked uploads:** large files (notably videos) upload in chunks via [ChunkedUploadController](app/Http/Controllers/ChunkedUploadController.php). The frontend driver is [useChunkedUpload.js](resources/js/Composables/useChunkedUpload.js). `finalize()` seeds a new `Slide`'s primary `slide`-type `SlideMedia` row; allowed MIME types per media type come from `config('slides.media_types')` rather than a hardcoded list.
- **Attaching additional media to an existing slide** (overlay, flyers, social image, …) goes through a small `ManagesSlideMedia` trait ([app/Http/Controllers/Concerns/ManagesSlideMedia.php](app/Http/Controllers/Concerns/ManagesSlideMedia.php)) shared by every area's slide controller, backing each area's `.../{slide}/media` routes and the [MediaManager.vue](resources/js/Components/MediaManager.vue) component on the Edit pages.
- **SVG safety & the overlay editor.** Every uploaded SVG is sanitized before it is web-reachable ([SvgSanitizer](app/Services/SvgSanitizer.php): no scripts/handlers/foreignObject, only `#fragment` or PNG/JPEG/GIF data-URI hrefs), since files are served straight off the public disk. See *SVG security model* below for the full picture and the rules for new code. The QR design controls (`QrDesigner`/`QrPreview`) are also used on their own by the fully client-side **QR Code Creator** (`/qr-code`, [Pages/QrCode.vue](resources/js/Pages/QrCode.vue), linked from the user menu for any signed-in user), which downloads the code as SVG or PNG without contacting the server.
- **Slide library.** Site admins keep a shared library of **backgrounds** (image/video) and **overlay templates** (Admin → Library, [Admin/LibraryController](app/Http/Controllers/Admin/LibraryController.php), one `library_items` table with `kind`). A slide built from it gets a normal `slide` `SlideMedia` row whose `disk_path`/thumbnail/poster are the library's paths: nothing is copied, so 100 churches using one background share one file. New code that stores or frees library files must go through `LibraryFiles`.

It is correct (a slide's cache file is never shared, so removing one slide can't break another) and only wasteful, which matters mainly for large videos on small SD cards. Deliberately not fixed, as it isn't expected to matter normally. If it does: key shared files on the device by a hash of the URL (e.g. `lib-<hash>.<ext>`), download each once, reference-count the many `unlink` call sites in `sync.py`, and add a `test_sync_slides.py` case with two slides sharing a URL; devices only get it with a new kiosk release.

### Storage tiers

Single-host installs keep every file on the local `public` disk (served from `/storage`). With `MEDIA_OFFLOAD_DISK=r2` ([config/media.php](config/media.php)), large files move to Cloudflare R2 (no egress fees) and are served from the bucket's public custom domain. [MediaStore](app/Support/MediaStore.php) is the only code that knows this:

- **Where a file lives** is a per-row `disk` column on `slide_media` and `slide_announcer_releases` (default `public`). It is a `SlideMedia::VERSION_FIELDS` entry, so each resize variant records its own disk. Thumbnails, posters and overlay composites are always on `public`.
- **What moves:** [OffloadMedia](app/Jobs/OffloadMedia.php) (dispatched by `GenerateThumbnail`) moves files that pass `MediaStore::eligible()`: a type on the allowlist and at least `MEDIA_OFFLOAD_MIN_BYTES`. **SVG never moves**, because it relies on the local server's sandbox CSP (see *SVG security model*). Do not add it to `offload_mimes`. A video moves only once its poster exists. Order: copy and verify, then flip `disk`, then delete the local file. [OffloadRelease](app/Jobs/OffloadRelease.php) does the same for release files, adding a sha256 fragment to the key, because version-named keys could be reused and a CDN caches them as immutable.
- **Reading:** links use `file_url` / `SlideAnnouncerRelease::url()` (the disk's public URL). Server-side processing calls `SlideMedia::localPath()`, which returns the real path, or for an offloaded file a copy in [MediaCache](app/Support/MediaCache.php) (an LRU cache bounded by `MEDIA_CACHE_MAX_BYTES`; a file used within `MEDIA_CACHE_MIN_AGE` minutes is never evicted; `media:prune-cache` runs every 15 minutes). Attachment downloads use `downloadResponse()`, which redirects to a signed R2 URL. Deleting uses `SlideMedia::deleteFiles()` / `SlideAnnouncerRelease::deleteFile()`. **New code must not call `Storage::disk('public')->path()/url()/delete()` on a media row's `disk_path`.** The exception is a just-uploaded file, which is always local.
- **Releases wait for the offload disk:** while release offloading is on, `SlideAnnouncerRelease::awaitingOffload()` holds a release that is still local back from the heartbeat (`*_update_available` false, no URL) and from the entity disk-image links, until `OffloadRelease` has moved it. A fleet therefore never downloads an update from the web host. Every device updater generation acts only on `*_update_available`, so no device change is needed. This can be turned off with `MEDIA_RELEASES_WAIT_FOR_OFFLOAD=false`.
- **Devices:** the kiosk sync downloads `file_url` directly (no redirects followed) and re-downloads whenever the URL changes. Media URLs must therefore stay direct and stable: public URLs, never presigned. Offloading changes a file's URL once.
- **Browsers** `fetch()` media (MediaManager resize, QR scan), so the bucket needs a CORS rule for `APP_URL`.
- **Deletion and restore:** deleting an offloaded file moves it under `media.trash_prefix` (`trash/`) in the bucket instead (`MediaStore::delete()`). A bucket lifecycle rule purges it later, so a restored older backup still finds it. [MediaInventory](app/Support/MediaInventory.php) lists every file the database refers to. Backups record the offloaded ones in `manifest.json` (`offloaded_objects`), and `media:verify` checks them all: `--restore-trash` brings trashed files back, and `--mirror=<dir>` checks an rclone copy of the bucket. `media:localize --relink` points rows at files already copied back to local disk. The restore procedure is in INSTALLING.md (*Backing up and restoring with R2*).
- **Backfill / switching back:** `media:offload [--dry-run]`, `media:localize`. Setup is in [INSTALLING.md](INSTALLING.md#offloading-large-files-to-cloudflare-r2-optional).
- **Other providers:** nothing above is R2-specific except the `r2` disk config. Backblaze B2 has been assessed but not implemented; INSTALLING.md lists what would change (*Other S3-compatible providers*).

### SVG security model

SVG is not an inert image format: it can carry `<script>`, event handlers and `javascript:` links, and an SVG opened as a document runs them in the application's origin (session theft; on a Slide Announcer device's kiosk browser, access to that device's localhost endpoints). Leaders and admins legitimately need to upload custom SVGs (overlays, social images), so SVG stays an allowed type and is made safe in layers. **Code review note: SVG being an allowed upload type is a deliberate, defended decision, not an open finding.** A review should check that the layers below still hold, not re-raise "SVG can carry script".

1. **Sanitize before the file is web-reachable.** `ChunkedUploadController::chunk()` assembles an SVG in the *private* chunk directory (`storage/app/chunks`), runs [SvgSanitizer](app/Services/SvgSanitizer.php) on it, and only then writes the clean result to the public disk. An SVG that is invalid, unparseable (including XXE/DOCTYPE entities), has no usable dimensions or exceeds 5 MB is rejected with a 422 and nothing is left behind. The upload endpoint is reachable by any signed-in user (attaching is role-gated, uploading is not), which is why sanitizing happens here and not only at attach time. An upload that is never attached therefore cannot leave a raw SVG on the public disk. `ManagesSlideMedia` sanitizes again on attach and on overlay save as defence in depth (it is idempotent).
2. **What the sanitizer does.** [enshrined/svg-sanitize](https://github.com/darylldoyle/svg-sanitizer) strips scripts, `on*` handlers, `foreignObject` and remote references; `SvgSanitizer` additionally drops any `href` that is not a local `#fragment` or an embedded PNG/JPEG/GIF data URI. `<style>` is **kept** (remote `@import` and remote `url()` are removed) so an embedded `data:` font in an `@font-face` survives: that is the intended route to custom fonts (embed the font in the SVG at save time), and it works when the SVG is shown through `<img>`. **Overlay fonts:** the editor offers a fixed set of OFL fonts (Inter and Noto Serif as the basic sans/serif and default, plus display, script and logo faces; variable fonts are pinned to static 400/700 instances by the build script) ([fonts.js](resources/js/Composables/overlay/fonts.js)). On save, `embedFontCss()` base64-embeds only the faces the text actually uses (~20–35 KB per face, Latin/Latin-1 WOFF2 subsets in `public/fonts/overlay/`); the editor canvas loads the same files through a page `<style>`. librsvg ignores `@font-face` and can't read WOFF2, so thumbnails/PPTX use TTF subsets in `resources/fonts/overlay/` via a fontconfig file ([OverlayCompositor::fontConfigFile](app/Services/OverlayCompositor.php), template in `docker/fontconfig/`). The Docker image installs `rsvg-convert`, fontconfig and DejaVu (the generic monospace face and a last-resort fallback; the bundled fontconfig file also points the generic sans-serif/serif at Inter/Noto Serif); the same `rasterizeSvg()` backs listing thumbnails, single-slide/zip downloads and the PPTX, so all three draw an overlay identically. Only the generic families ("System sans-serif" etc., kept for older overlays) can differ between browser and server; the bundled fonts match everywhere, which is why Inter is the default. Regenerate both sets with `scripts/build_overlay_fonts.py <fonts-folder>…` and add the family to `CUSTOM_FONTS`. Keep the library current: it is a security dependency, so treat advisories and releases as security updates.
3. **Display through `<img>` or rasterization, never inlined into the app's DOM.** Slides, thumbnails (`rsvg-convert`) and device playback render SVG as an image, where script never runs regardless of sanitizer quality. The overlay editor reads the SVG into its own model rather than injecting it. This makes the sanitizer a second layer behind the rendering context, not the only one. **Do not inline user SVG markup into a page** (`v-html`, `innerHTML`) without also doing everything under "If inlining is ever needed".
4. **Web-server backstop.** `/storage/*.svg` is served with `Content-Security-Policy: sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:` and `X-Content-Type-Options: nosniff` ([docker/nginx.conf](docker/nginx.conf); other installs, see [INSTALLING.md](INSTALLING.md)). If a sanitizer bypass ever existed, an SVG opened directly in a tab still could not run script. The header is ignored when the SVG is used as an `<img>`, so it does not affect display.
5. **Extension and type.** The stored extension comes from the validated mime type (`config('slides.mime_extensions')`), never the client's filename, so a file cannot be stored as `.html`/`.php`.

**If inlining is ever needed** (for example page-hosted CSS fonts or DOM interaction), the sanitizer alone is not enough, because a single bypass becomes script in the app origin. Do all of: render inside an `<iframe sandbox>` with neither `allow-scripts` nor `allow-same-origin` (a unique origin with no access to cookies, the app or localhost endpoints), or if it must be in the DOM, sanitize again client-side (DOMPurify, SVG profile) and scope its CSS (Shadow DOM or selector prefixing) so a `<style>` block cannot restyle the app; and add a nonce-based `script-src` Content-Security-Policy to the app (none exists today; only `WidgetDataController` sets one on its responses), which is the strongest backstop against any XSS.

Tests: [SvgUploadSanitizationTest](tests/Feature/SvgUploadSanitizationTest.php) (chunked path), [OverlaySourceTest](tests/Unit/OverlaySourceTest.php) (sanitizer rules).

## Slide Announcer device code

The Raspberry Pi kiosk is split in two: the product-neutral platform (OS image,
Wi-Fi/settings shell, pairing, updates) is the `slideannouncer/` git submodule,
and everything signage-specific — slide sync, the slideshow, LAN video, widgets
on the device — lives in [kiosk-products/slideannouncer/](kiosk-products/slideannouncer/)
and is built into the platform with `PRODUCT_ROOT`. The server side of the
pairing/heartbeat contract is the `SlideAnnouncer*Controller`s; see
`slideannouncer/docs/DEVICE_CONTRACT.md` and `PRODUCTS.md`.

### Device and release versions

A device's version is the pair `<platform>_<product>` (e.g. `0.4.1_0.1.0`), with an underscore so it is safe in file names and URLs. The local app is `local-app/VERSION` + the product's `VERSION`; the OS image is `image-builder/VERSION` + the product's `image/VERSION` (see `slideannouncer/docs/PRODUCTS.md`). The server treats a plain `X.Y.Z` (a device from before pairs) as product `0.0.0`. [SlideAnnouncerRelease](app/Models/SlideAnnouncerRelease.php) accepts both forms in uploads and filenames (`VERSION_PATTERN`, `parseFilename()`, which also reads a local-app archive's name), orders them platform-then-product (`compareVersions()`, used by the heartbeat to decide a full release is newer), and matches hotfixes by **exact** `required_base_version`. Release types are `full`, `hotfix`, `disk_image` (SD-card image) and `virt_image` (the `build.sh --virt` UEFI image for arm64 VMs, named `…-virt.img.xz`; its own tag slot, never an OTA candidate). Entity users download both from `Entity/SlideAnnouncers`, where VM images sit in a separate amber "VM TESTING ONLY" block linking to the image-builder README. So a product-only change (`0.4.0_0.1.0` → `0.4.0_0.1.1`) and a platform-only one (`0.4.0_0.1.0` → `0.4.1_0.1.0`) are each a release or hotfix of their own.

### Backups

One service, [BackupService](app/Services/Backup/BackupService.php), builds every backup: `backup:create` (CLI), the scheduler ([routes/console.php](routes/console.php), database-only), the Docker entrypoint (`--if-migrations-pending --tag=pre-migrate` before `migrate`) and the admin page ([BackupController](app/Http/Controllers/Admin/BackupController.php) → queued [RunBackup](app/Jobs/RunBackup.php)). An archive is a ZIP: `manifest.json`, `database.sql` (from `mysqldump` via [MysqlDumper](app/Services/Backup/MysqlDumper.php), swappable through `DatabaseDumper`), and in full mode `files/public/` + `files/private/` (never the backups dir itself). The `APP_KEY` is never included, only a fingerprint. Archives live on `config('backup.disk')` under `backups/`; the `backups` table is only metadata and is rebuilt from the manifests by `syncFromDisk()` (a restore replaces the table with an older copy). Only scheduled and pre-migrate/pre-restore archives are pruned ([config/backup.php](config/backup.php)). Restore is CLI-only (`backup:restore`: manifest checks, safety backup, maintenance mode, load, migrate, files). `Widget.settings` uses a tolerant cast so a different `APP_KEY` reads as "not configured". See [docker/README.md](docker/README.md#backups).

## Notifications

Per-user in-app notifications with optional email. Each event creates **one row per recipient** in `notifications`. This is Laravel's database-notifications table, plus four columns:

- `category`
- `archived_at`: "cleared", which is separate from `read_at`
- `email_mode`: the recipient's email choice when the row was created
- `emailed_at`

The model is [Notification](app/Models/Notification.php). `type` is a short key that the frontend renders through `notifications.types.*` in the locale files. Emails render it through `lang/<locale>/notifications.php`, so keep the two in step. `data` holds `params`, an optional `url`, and a `slide_id` whose thumbnail is looked up at display time.

- **Creating:** always go through [Notifier::send()](app/Services/Notifier.php). It takes a category, a type, recipients, and a payload (or a per-user closure). It applies preferences, skips banned users and non-admins in admin-only categories, writes rows with a chunked bulk insert, and queues one `SendNotificationEmail` per "Right away" recipient. Notifier never sends mail itself. Fan-outs that can reach many people run in queued jobs.
- **Categories** are defined in [config/notifications.php](config/notifications.php), each with an audience (`everyone` / `managers` / `admin`) and default inbox and email settings. Per-user choices are UserSettings (`notify.<category>.inbox|email`), read and written only by [NotificationPreferences](app/Support/NotificationPreferences.php). The choices are edited on the Profile page.
- **Events:**
  - Review decisions and new submissions: [SlideNotifications](app/Notifications/SlideNotifications.php), called from the admin and upload controllers.
  - Team joins: [TeamNotifications](app/Notifications/TeamNotifications.php), from `EntityInvitation::redeemFor`, `EntityPeopleController::store` and `GoogleController`.
  - New global, nearby and promo slides: [SlideAvailabilityNotifications](app/Notifications/SlideAvailabilityNotifications.php). It runs from `SyncShowAutoFillForSlide`, `AnnounceSlideAvailability` and `DistributeGlobalSeparateShow`.
    - `Show::syncAutoFillForSlide()` and `restoreImmutableSlide()` return the show ids they attached, so each notice can say which of a manager's shows the slide landed in.
    - `slides.announced_at` and `global_show_templates.announced_at` are claimed atomically, so a slide is announced only once.
  - Started and expired slides: `notifications:slide-schedule`, every 15 minutes, using `slides.start_notified_at` / `expiry_notified_at`.
  - Slide Announcer devices: [DeviceNotifications](app/Notifications/DeviceNotifications.php), sent to the managers of the device's church.
    - `device_temperature`: the heartbeat controller calls it with each reported `cpu_temp_c`. At or over the admin-set limit (default 70 °C) it sends one notice and stamps `slide_announcers.temp_alert_at`. The alert re-arms only once the device is 5 °C below the limit and an hour has passed.
    - `device_status` (opt-in, off by default): `notifications:device-status` runs every 5 minutes and reports devices that missed `slide_announcer.offline_after_missed_heartbeats` (3) heartbeats, stamping `offline_notified_at`. The device's next heartbeat clears the stamp and sends "back online". Devices silent for more than 24 hours are stamped without a notice.
- **UI:**
  - The bell is [NotificationBell.vue](resources/js/Components/NotificationBell.vue), in `UserMenu` and `UserMenuAdmin`. Its badge comes from the shared prop `unreadNotifications`, and its dropdown from `GET /notifications/recent`.
  - The inbox and archive are at `/notifications` ([NotificationController](app/Http/Controllers/NotificationController.php)). Every query there is scoped to the signed-in user. `/notifications/{id}/open` marks a notification read and redirects, to same-site paths only.
- **Email:**
  - The digest: `notifications:send-digest` runs daily at the admin-set time and queues one `SendNotificationDigest` per user. A digest leaves out items already read in the app.
  - Every email carries a signed per-category unsubscribe link plus RFC 8058 `List-Unsubscribe` headers (the POST route is CSRF-exempt). GET only shows a confirm button.
  - Emails are written in the user's `locale` setting, which [RememberUserLocale](app/Http/Middleware/RememberUserLocale.php) records from `Accept-Language` once per session.
- **Admin → Notifications** ([NotificationSettings](app/Support/NotificationSettings.php), stored in `app_settings`) controls:
  - email on/off (off by default, so nothing builds up before a mailer is configured)
  - digest time
  - how long cleared notifications are kept (`notifications:prune`, daily)
  - how long before un-cleared inbox items are archived automatically
  - the device over-temperature limit
  - a "send me a test email" button

Everything above relies on the queue worker and the scheduler. The Docker image runs both (`docker/supervisord.conf`).

## Console (Artisan) commands

In [app/Console/Commands/](app/Console/Commands/) — primarily for bootstrapping and data import:

- **Users:** `user:create`, `user:list`, `user:setrole`, `user:setpassword`
- **Churches/entities:** `church:load` (scrape a conference from adventistdirectory.org into `adventist_entities`), `church:list`, `church:detail`, `entity:sync` (distill into `entities`), `entity:assign` (grant/revoke a user's entity role: `admin`=leader, `editor`, `viewer`)
- **Directory import UI:** **Admin → Directory Import** ([DirectoryImportController](app/Http/Controllers/Admin/DirectoryImportController.php), services in [app/Services/DirectoryImport/](app/Services/DirectoryImport/)) is an upload → preview → confirm flow. Churches come from the pastor-directory `data.json` (`churchAddresses`, keyed by `orgCode` = `org_mast_id`) or a `church:export` CSV into `adventist_entities`, optionally followed by the `entity:sync` logic ([EntitySyncer](app/Services/DirectoryImport/EntitySyncer.php)). Pastors (`data.json` `pastors`, or a CSV) become users, with entity role `admin` on their churches; `users.created_by_import` / `users.in_latest_import` drive the "imported users no longer in master data" report on that page.
- **Coordinates:** `entity:geocode [--limit=N] [--dry-run]` fills missing `entities.latitude/longitude` from the free U.S. Census batch geocoder ([EntityGeocoder](app/Services/DirectoryImport/EntityGeocoder.php); street addresses only; never overwrites existing coordinates). The same lookup is a background job ([GeocodeEntities](app/Jobs/GeocodeEntities.php)) behind a button on Admin → Directory Import. `EntitySyncer` keeps existing coordinates when the source row has none.
- **Languages:** `language:add`, `language:list`
- **Widgets:** `widget:install <dir|zip>…` (same checks as the admin upload; e.g. `php artisan widget:install resources/widgets/clock resources/widgets/calendar`)
- **Thumbnails:** `slide:resync-thumbnails [--all] [--now]` rebuilds slide+overlay composite previews (fixes stale "ghost" previews); queued by default.

## Where to start when changing things

- **Add/alter a slide-visibility rule** → a scope on [Slide](app/Models/Slide.php), then the relevant controller query.
- **Change who can do what** → the role helpers on [User](app/Models/User.php) plus middleware in [app/Http/Middleware/](app/Http/Middleware/) and the route groups in [routes/web.php](routes/web.php).
- **Touch the upload pipeline** → [ChunkedUploadController](app/Http/Controllers/ChunkedUploadController.php), [ImageValidationService](app/Services/ImageValidationService.php), [GenerateThumbnail](app/Jobs/GenerateThumbnail.php).
- **UI** → the matching component in [resources/js/Pages/](resources/js/Pages/); shared props come from [HandleInertiaRequests](app/Http/Middleware/HandleInertiaRequests.php).
- **Browser resizing (AI upscale / downscale)** → [useUpscaler.js](resources/js/Composables/useUpscaler.js), [useImageResize.js](resources/js/Composables/useImageResize.js), [UpscalerSettings](app/Support/UpscalerSettings.php), [ImageResize](app/Support/ImageResize.php), `ManagesSlideMedia::resizeMediaForSlide`, [SlideMedia](app/Models/SlideMedia.php) variants (`original` + `resized`).
- **Config knobs** → [config/slides.php](config/slides.php), [config/widgets.php](config/widgets.php) and `.env` ([.env.example](.env.example)).
- **Widgets** → host contract in [widgetHost.js](resources/js/Composables/widgets/widgetHost.js), server side in [app/Services/Widgets/](app/Services/Widgets/), author guide in [resources/widgets/README.md](resources/widgets/README.md), app-specific notes in [resources/WIDGETS.md](resources/WIDGETS.md).

Tests live in [tests/](tests/) (PHPUnit; currently Breeze auth + profile coverage).
